### SQL / integration (реальный PostgreSQL, миграции проекта, роли как в Supabase) — 62 теста

* **Конкурентная запись**: 6 параллельных транзакций на одно время при двух
  столах → ровно 2 заказа, 4 × `slot_taken`, номера заказов без дублей.
* **EXCLUDE**: прямая вставка пересекающегося диапазона отвергается
  `resource_occupancies_no_overlap`.
* **Два ресурса**: второй заказ уходит на второй стол, третий — `slot_taken`,
  слот исчезает из выдачи, соседнее время доступно; смешанная корзина
  занимает стол и коптильню, оба диапазона кончаются в момент выдачи.
* **Многодневная занятость**: копчение 48 ч + буфер 60 мин занимает
  непрерывный диапазон через границу суток; ближайший слот ≥ now + 49 ч;
  заказ на сутки позже на той же коптильне отвергается; столы не затронуты.
* **Блокировка**: блокировка владельца делает ресурс недоступным; блокировка
  поверх заказа и заказ поверх блокировки — `resource_busy`/`slot_taken`;
  снятие освобождает.
* **Перенос**: атомарный, версия +1, старое напоминание отменено, новое
  создано на новое время; повтор с тем же ключом — replay, с другим
  payload — `idempotency_conflict`; **неудачный перенос оставляет исходный
  диапазон и время без изменений**; сдвиг внутрь собственного диапазона
  работает. Дедлайн изменений действует для покупателя, но не для владельца.
* **Идемпотентность**: повтор `place_order` с тем же ключом → тот же заказ и
  **тот же токен**; 3 параллельных повтора → 1 заказ; в БД только SHA-256
  токена (32 байта).
* **RLS / изоляция tenant'ов**: anon не читает orders, order_items, payments,
  push_subscriptions, notification_jobs, order_requests, occupancies,
  tenant_members, private.*; не исполняет place_order, get_pickup_slots,
  publish_tenant, claim_notification_jobs, rate_limit_hit, llm_budget_*,
  owner_*; не видит draft-магазины; не пишет каталог. Владелец A не видит
  заказы B, получает `forbidden` в owner_* для B и `order_not_found` при
  подмене id; `access_token_hash` недоступен; прямые INSERT/UPDATE запрещены.
  Составной FK отвергает строку со смешанными tenant'ами.
* **Историческая цена**: после смены цены владельцем старый заказ хранит цену
  снимка, перенос не переоценивает, новый заказ — по новой цене; поля
  цены/суммы/tenant от клиента игнорируются.
* **Платежи и статистика**: визиты, выданные заказы (по сумме после
  взвешивания), полученные платежи (минус возвраты) и ожидаемые выдачи
  считаются раздельно; ключа `revenue` нет; возврат больше оплаты — ошибка;
  повтор платежа с тем же ключом — replay; границы периода и timezone
  возвращаются вместе с цифрами.
* **Outbox**: дедупликация по `dedupe_key`; два воркера не получают одно
  задание (SKIP LOCKED); чужой воркер не может завершить задание; истёкший
  lease перехватывается, attempts растёт; экспоненциальный backoff; после
  переноса/отмены устаревшие напоминания отменяются, «проскочившее»
  устаревшее задание отменяется при claim; preview/demo → только `skipped`;
  цели push разделены по аудитории.
* **Timezone/исключения**: слоты на локальной сетке Asia/Novosibirsk;
  закрытый день и укороченные часы; подготовка до открытия не допускается;
  локальные 10:00 сохраняются через переход DST (America/New_York);
  горизонт и запрет прошлого.
* **Публикация**: переиздание сохраняет заказы и фото владельца,
  деактивирует удалённые товары, тот же hash не меняет версию; второй
  магазин не заменяет первый; live требует готовности и удаляет демо.
* **Общие счётчики**: 25 параллельных хитов → ровно 10 разрешено;
  12 параллельных резервов LLM при лимите 5000 → ровно 5, commit корректирует.

### Unit — 34 теста

* **Роутер ИИ** (выбранный детерминированный pre-router): владельческие
  интенты и периоды, поиск по номеру/телефону, клиент никогда не
  маршрутизируется в owner-инструменты (найден и исправлен баг: `\w` не
  матчит кириллицу).
* **Оркестрация ИИ** со *скриптовой тестовой заглушкой модели* (не
  интеграция с провайдером): обязательный инструмент `stats` выполняется
  до модели и передаётся ей как tool-сообщение; tenant_id в схемах
  инструментов отсутствует, подставленный моделью `tenant_id` игнорируется;
  клиентский scope не может вызвать `stats`/`find_orders`; tool loop
  ограничен; при отказе провайдера от tools — JSON-intent протокол;
  без модели, при превышении бюджета и недоступности — ответ по данным.
* **Web Push**: шифрование aes128gcm расшифровывается стороной получателя;
  VAPID JWT проверяется как валидная подпись ES256 для origin push-сервиса;
  404/410 → подписка «gone».
* **ICS**: RFC 5545, свёртка строк ≤ 75 октетов, напоминание −2 ч, отмена.
* **Конвейер**: схема и перекрёстные проверки, контраст акцента, детерминированный
  hash, отдельные манифесты на магазин и на кабинет, оболочка без бизнес-имён
  в общем шаблоне, порядок правил `_redirects`.

### HTTP через локальный стек — 6 тестов

gateway → Edge Function `public-api` → PostgREST → Postgres, Supabase Auth:
слоты → заказ (повтор возвращает тот же токен) → получение → ICS → перенос →
отмена; маппинг ошибок SQL в HTTP (400/404/409); rate limit 429 после 10
запросов с одного адреса; владелец по паролю видит свои заказы, `forbidden`
для чужого магазина, anon получает 42501; `ai-chat`: владелец получает
статистику из SQL-инструмента, клиентский scope не достаёт owner-инструменты,
без JWT — 401, чужой владелец — 403; **outbox → зашифрованный Web Push**:
`notify-dispatch` забирает задания, отправляет push (на тестовый приёмник),
полезная нагрузка расшифровывается ключами «браузера», повторный запуск
ничего не дублирует; неверный cron-секрет — 403.

### Playwright — 4 сценария

1. **Покупатель → владелец**: каталог → карточка в bottom sheet → корзина →
   время выдачи от сервера → контакты → «Заказ принят»; заказ в «Мои заказы»
   после перезагрузки; владелец входит, находит заказ по номеру, видит
   состав, отмечает «Собран»; покупатель видит новый статус; выход удаляет
   сессию из localStorage.
2. **Изоляция PWA**: у `/s/rebro/` и `/s/taiga/` свои service worker scope,
   свои имена кэшей `shop-<slug>-client-*`, свой манифест; в кэшах нет
   `/rest/v1`, `/functions/v1`, `/auth/v1`; кэши одного магазина не содержат
   файлов другого; **офлайн deep link `/s/taiga/orders/…` отдаёт оболочку
   именно taiga** и явное состояние «Нет соединения».
3. **Кабинет**: отдельный scope `/s/rebro/owner/` и `owner.webmanifest`; после
   выхода нет API-ответов в кэшах и сессии в хранилище.
4. **Дизайн-фундамент на реальных страницах**: кнопки Astryx сохраняют
   padding и фон на витрине и в лениво загружаемом кабинете, акцент магазина
   доходит до primary-кнопки. Тест добавлен после найденной визуальной
   регрессии: при выносе кабинета в отдельный чанк CSS Astryx начал
   загружаться раньше объявления порядка `@layer`, и preflight Tailwind
   обнулял стили. Исправлено инлайн-объявлением слоёв первым в `<head>`.

### Конвейер вручную (выполнено)

`tenant:new --from rebro` → правка → `tenant:validate` → `tenant:publish
--invite-owner --demo` → `npm run build` → `tenant:verify` для нового и обоих
старых магазинов (26/26 у каждого) → `tenant:publish --live` (удалено 15

## 2. Не выполнено — требует внешних ресурсов

| Проверка | Почему не выполнена | Как выполнить |
|---|---|---|
| Деплой миграций в реальный Supabase (PG 17, storage-политики, pg_cron, pg_net, Vault) | Нет credentials проекта | `supabase db push`, затем SQL из SETUP.md §3–4; `npm run test:stack` нельзя направить на прод — используйте `tenant:verify` |
| Загрузка фото владельцем в **Supabase Storage** | Локально работает адаптер `/storage/v1`, не Storage | В проекте: Каталог → товар → фото; проверить объект в `tenant-media/<tenant_id>/owner/` и что запись в чужую папку отклоняется |
| Supabase Cron → `notify-dispatch` | Нет pg_cron/pg_net локально; воркер вызывался напрямую в тесте | `select * from cron.job_run_details` после деплоя |
| Доставка push через реальные сервисы (FCM, Mozilla, Apple) | Хосты push-сервисов недоступны; шифрование и VAPID проверены криптографически | Включить уведомления в кабинете на телефоне, оформить заказ с другого устройства |
| Реальная LLM | `LLM_BASE_URL` не задан, провайдер для ключа неизвестен, все LLM-хосты заблокированы; ключ из сообщения **никуда не записан** | Задать `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL` в секретах функций, `LLM_TOOL_MODE=auto`; проверить вопросы «сколько оплат сегодня», «заказы на завтра» |
| Cloudflare Pages (в т.ч. плейсхолдеры в `_redirects`) | Нет токена; правила проверены локальным сервером с той же семантикой | `tenant:publish --deploy`, затем `tenant:verify --site https://…` |
| Установка standalone на реальных iPhone/Android, push на iOS из установленного приложения, стартовые экраны | Нет устройств | Safari → «На экран Домой» для `/s/<slug>/` и отдельно `/s/<slug>/owner/`; проверить иконку, стартовый экран, push |
| Визуальная сверка с Figma | Figma недоступна | — |

## 3. Известные ограничения

* Основной JS-чанк витрины ≈ 150 КБ gzip + общий чанк Astryx ≈ 175 КБ gzip;
  кабинет вынесен в отдельные ленивые чанки.
* Номер телефона валидируется по количеству цифр (10–15), без проверки
  страны.
* Время выдачи владелец задаёт свободно (`datetime-local` во времени
  магазина); покупатель — только по сетке слотов.
* Генерированные изображения — заглушки до замены реальными фото.
